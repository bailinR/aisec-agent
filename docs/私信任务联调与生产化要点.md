# 私信任务联调与生产化要点

日期：2026-07-16

本文沉淀评论采集系统调用私信系统时最常用的信息：接口调用、异步任务判断、重试与死信、人工处理、鉴权设计、账号限流、部署消费排查。

## 1. 当前链路

```text
采集评论系统
  -> POST /api/v1/douyin/private-message/tasks
  -> Web API 写入 Redis
  -> worker 消费 dm:queue:auto_pending
  -> 有 message 时直接使用；否则生成私信
  -> Playwright 打开抖音主页并发送
  -> 写回任务状态、失败字段、截图 URL
```

提交任务接口是异步接口。`POST /tasks` 返回 `accepted: 1` 只代表任务已入队，不代表已经发送完成。是否真的发送，要查询：

```http
GET /api/v1/douyin/private-message/tasks/{task_id}
```

正式任务支持可选字段 `message`。当 `message` 为非空字符串时，worker 跳过私信生成，直接使用该内容执行发送；未传或为空时，保持原有的“先生成、再发送”流程。

## 2. Postman 判断顺序

1. 健康检查：

```http
GET /api/health
```

2. 提交任务：

```http
POST /api/v1/douyin/private-message/tasks
```

3. 查任务详情：

```http
GET /api/v1/douyin/private-message/tasks/{task_id}
```

4. 查队列和 worker 状态：

```http
GET /api/v1/douyin/private-message/tasks?limit=20
```

判断重点：

- `pending / queued`：任务已入队，worker 还没消费。
- `running / processing`：worker 正在执行。
- `success` + `sent=true`：发送成功。
- `retry_wait`：等待自动重试。
- `manual_required`：需要人工处理账号、验证、风控或脚本。
- `failed` + `dead_letter=true`：最终失败，不再自动重试。
- `failed` + `failure_code=login_required`：当前发送任务失败，需要重新登录后重新提交；`manual_required=true` 仍用于提示人工恢复登录态。

## 3. 任务详情重点字段

任务查询接口返回里重点看 `data.result`：

| 字段 | 用途 |
|---|---|
| `status` | 任务状态 |
| `queue_status` | 队列状态 |
| `sent` | 是否确认发送 |
| `success` | 业务任务是否处理成功；对方隐私限制时为 `true`，但 `sent=false` |
| `send_status` | 发送结果，如 `sent` / `failed` / `retry_wait` / `account_switched` / `recipient_privacy_restriction` |
| `reply` | 生成出的私信内容 |
| `followup_message` | 首条私信发送成功后可继续发送的第二条内容，失败不影响主任务 |
| `followup_private_message_status` | 后续消息状态，如 `skipped` / `attempted` / `sent` / `failed_ignored` |
| `followup_private_message_detail` | 后续消息的执行细节或失败摘要 |
| `error` | 原始错误文本 |
| `error_code` | 内部错误码 |
| `failure_code` | 面向排查的失败码 |
| `failure_type` | `retryable` / `manual` / `final` |
| `failure_stage` | 失败阶段，如 `model_config` / `browser_runtime` / `send_confirm` |
| `failure_summary` | 人能直接看的失败摘要 |
| `failure_screenshot_url` | 失败截图访问地址 |
| `failure_screenshot_exists` | 失败截图文件是否存在 |
| `retry_count` | 已重试次数 |
| `max_retries` | 最大重试次数 |
| `next_retry_at` | 下次重试时间 |
| `retry_delay_seconds` | 下次重试延迟秒数 |
| `manual_required` | 是否需要人工处理 |
| `dead_letter` | 是否进入死信 |
| `manual_takeover` | 人工接管提示和可打开的目标主页 |
| `account_id` | 实际执行账号 |
| `account_switched` | 是否已自动切换账号 |
| `switched_from_account_key` | 切号前的账号 key |

## 4. 失败分类

### 可重试失败

这类失败通常是临时问题，worker 会进入 `retry_wait`：

- 网络超时。
- 模型超时。
- 页面加载超时。
- 偶发找不到元素。

典型字段：

```json
{
  "status": "retry_wait",
  "queue_status": "retry_wait",
  "failure_type": "retryable",
  "retry_count": 1,
  "next_retry_at": "2026-07-16 10:30:00"
}
```

### 不可重试失败

这类失败通常不是重试能解决的问题，会进入 `failed` / `dead_letter`：

- 参数缺失。
- 主页 URL 非法。
- Cookie 无效。
- 账号无权限。
- 模型 key 未配置。
- 运行环境缺少 Playwright。

典型字段：

```json
{
  "status": "failed",
  "queue_status": "dead_letter",
  "failure_type": "final",
  "dead_letter": true
}
```

### 人工处理失败

这类失败不是指一定要人工扫码，而是指 worker 自动重试大概率不会自愈，需要外部干预：

- 登录验证：上游给了 cookie，但当前环境里登录态不可用。
- 二次验证：平台要求短信、验证码、设备确认或安全验证。
- 账号风控：账号被限制私信、频率过高、发送被平台拦截。
- 页面结构疑似变化：脚本找不到私信按钮、输入框、发送按钮或页面流程变化。

典型字段：

```json
{
  "status": "manual_required",
  "queue_status": "manual_required",
  "failure_type": "manual",
  "manual_required": true,
  "failure_code": "verification_required"
}
```

登录态失效是一个特殊终态：当前任务直接返回 `status=failed`、`queue_status=failed`，同时保留 `failure_type=manual`、`manual_required=true` 和 `failure_code=login_required`。重新登录后应重新提交任务，不会自动重试原任务。

人工处理时先看：

1. `failure_summary`
2. `failure_screenshot_url`
3. `manual_takeover.url`
4. worker 日志

## 5. Redis 队列

| Key | 用途 |
|---|---|
| `dm:task:{task_id}` | 任务详情 |
| `dm:queue:pending` | 全局待处理队列 |
| `dm:queue:auto_pending` | 自动执行队列 |
| `dm:queue:pending:{account_key}` | 账号维度待处理队列 |
| `dm:queue:processing` | 正在处理 |
| `dm:queue:done` | 成功历史 |
| `dm:queue:failed` | 失败历史 |
| `dm:queue:retry_wait` | 等待重试，zset |
| `dm:queue:manual_required` | 等待人工处理 |
| `dm:queue:dead_letter` | 死信队列 |
| `dm:sent_targets:{account_key}` | 同账号已发送目标去重 |

当前默认：

- 任务 TTL：7 天。
- 最大重试：`DM_REDIS_DEFAULT_MAX_RETRIES = 1`。
- 重试延迟：`10s / 30s / 120s`。
- Redis 地址优先读取环境变量 `REDIS_URL`，默认 `redis://127.0.0.1:6379/0`。

## 6. 接口鉴权建议

当前生产对接建议用 HMAC 服务间签名，而不是长期裸 token。

上游每次请求生成：

```http
Authorization: AISec-HMAC client_id="comment_collector",timestamp="1721030000",nonce="随机字符串",signature="签名"
```

签名原文：

```text
HTTP_METHOD
PATH
TIMESTAMP
NONCE
BODY_SHA256
```

签名算法：

```text
signature = base64url(hmac_sha256(client_secret, 签名原文))
```

服务端验证：

1. 根据 `client_id` 找 `client_secret`。
2. 校验 `timestamp` 是否在 5 分钟内。
3. 用 Redis 记录 `nonce`，防重放。
4. 重新计算签名并用 `hmac.compare_digest` 比较。

临时内网联调可先用：

```http
Authorization: Bearer <AISEC_DM_API_TOKEN>
```

但正式接入建议升级 HMAC。

## 7. 账号发送限流建议

发送私信时不要只看任务队列，还要限制账号。

建议三层：

1. 单账号并发锁  
同一账号同一时间只允许一个 worker 操作。

```text
dm:lock:account:{account_key}
```

2. 频率限制  
示例策略：

- 每分钟最多 2 条。
- 每小时最多 20 条。
- 每天最多 80 条。
- 同账号同目标 7 天内不重复发，除非明确 `force_resend=true`。

3. 账号健康状态  
当前 Redis 账号状态保存在 `dm:account:{account_key}`，后台账号管理通过 `GET /api/v1/douyin/private-message/accounts` 读取。主要字段包括 `status`、`dy_private_message_note`、`next_available_at`、`hourly_limit` 和 `hourly_sent_count`。

当前状态：

- `active`
- `cooldown`
- `daily_limited`
- `login_invalid`
- `paused`
- `risk`
- `disabled`

处理规则：

- 登录失效：任务返回 `failed` 和 `failure_code=login_required`，账号标记为 `login_invalid`，`dy_private_message_note=账号登录失效，需要重新登录`。
- 今日上限：账号标记为 `daily_limited`，暂停到次日并优先切换其他可用账号。
- 私信频繁/系统繁忙：账号标记为 `cooldown`，写入 `next_available_at` 并优先切换账号。
- 小时上限：默认每小时 20 条，可通过 `AISEC_DM_HOURLY_LIMIT` 或账号的 `hourly_limit` 调整；达到后冷却至当前小时窗口结束并切换账号。
- 对方隐私限制：任务按业务处理成功，返回 `status=success`、`success=true`、`sent=false`、`send_status=recipient_privacy_restriction`，并保留 `failure_code` 和 `failure_reason`，不进入失败或死信队列。

## 8. 部署消费排查

如果提交任务成功但“没有发送”，先判断是没消费还是消费失败：

```http
GET /api/v1/douyin/private-message/tasks?limit=20
```

看：

- `counts.auto_pending`
- `counts.processing`
- `counts.failed`
- `counts.retry_wait`
- `counts.manual_required`
- `counts.dead_letter`
- `worker.enabled`
- `worker.alive`
- `worker.last_error`

常见结论：

- `auto_pending` 长期不动：worker 没启动、连错 Redis、消费队列不一致。
- `failed` 增加：worker 已消费，但执行失败。
- `manual_required` 增加：账号或页面需要人工干预。
- `retry_wait` 增加：临时失败，等待自动重试。

Docker 形态下，Web API 负责接请求和写 Redis，worker 容器负责消费和 Playwright。不要只看 API 容器健康就判断私信链路正常。

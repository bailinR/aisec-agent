# 数据中台对接抖音私信

本文给数据中台使用。当前私信接口是异步任务模式：数据中台提交任务后，按 `task_id` 查询结果；当前没有私信结果回调接口。

## 1. 基本接口

测试地址：`http://127.0.0.1:7860`

生产环境替换为实际 Web 服务地址。

### 提交任务

```http
POST /api/v1/douyin/private-message/tasks
Content-Type: application/json
```

请求示例：

```json
{
  "task_id": "comment_dm_20260820_000001",
  "account_id": "douyin_account_01",
  "account_cookie": "sessionid=xxx; sid_guard=xxx",
  "target_profile_url": "https://www.douyin.com/user/xxxx",
  "video_info": "视频内容摘要",
  "comment_info": "用户评论内容",
  "project_name": "项目名称",
  "message": "您好，看到您的留言了。"
}
```

说明：

- `task_id` 由数据中台生成，必须全局唯一，建议使用评论任务 ID，不要重复复用处理中任务的 ID。
- `account_id` 建议固定传入，便于识别实际发送账号和账号切换记录。
- `account_cookie` 是执行发送所需的账号登录信息，不能写入普通业务日志。
- 传 `message` 时直接发送该内容；不传时由私信系统生成消息。
- 正式任务默认自动进入发送队列。

提交成功只表示“任务已入队”，不表示消息已经发出。

成功响应的重点字段：

```json
{
  "code": 0,
  "msg": "success",
  "data": {
    "accepted": 1,
    "task_ids": ["comment_dm_20260820_000001"]
  }
}
```

### 查询任务

```http
GET /api/v1/douyin/private-message/tasks/{task_id}
```

以 `data.result` 为数据中台最终判断依据：

```json
{
  "code": 0,
  "msg": "success",
  "data": {
    "task_id": "comment_dm_20260820_000001",
    "result": {
      "status": "success",
      "queue_status": "done",
      "success": true,
      "sent": true,
      "send_status": "sent",
      "failure_code": "",
      "failure_reason": "",
      "account_id": "douyin_account_01",
      "account_switched": false,
      "next_retry_at": ""
    }
  }
}
```

## 2. 状态判断规则

数据中台不要只判断 `status`，要同时看 `success`、`sent`、`send_status` 和 `failure_code`。

| 返回结果 | 数据中台处理 |
|---|---|
| `pending` / `queued` | 已入队，继续轮询 |
| `running` / `processing` | worker 执行中，继续轮询 |
| `retry_wait` | 系统会自动重试；等待 `next_retry_at`，不要重复提交同一任务 |
| `retry_wait` + `send_status=account_switched` | 原账号不可用，系统已切换账号；继续轮询原 `task_id` |
| `success` + `sent=true` | 私信确认发送成功 |
| `success` + `sent=false` + `failure_code=recipient_privacy_restriction` | 业务处理完成，但平台因对方隐私设置未实际发送；不要按系统失败重试 |
| `failed` + `failure_code=login_required` | 任务失败，提示“需要重新登录”；账号登录失效，重新登录后重新提交 |
| `failed` + `failure_code=stranger_daily_limit` | 今日陌生人私信已达上限；当天不要继续提交该账号任务 |
| `failed` + `failure_code=hourly_limit_reached` | 账号小时上限已达；不要立即重提，等待账号恢复或改用其他账号 |
| `failed` + `failure_code=rate_limited/platform_busy` | 当前没有可切换账号或自动重试已结束；等待账号冷却后再提交 |
| `failed` / `dead_letter=true` | 最终失败，不再自动重试，记录 `failure_reason` |
| `manual_required` | 需要人工处理二次验证、风控或页面异常，记录 `manual_takeover` 信息 |

建议的业务映射：

```text
success=true, sent=true  -> 发送成功
success=true, sent=false -> 已处理但未送达（例如对方隐私限制）
status=retry_wait       -> 处理中，等待系统重试
status=failed           -> 发送失败
status=manual_required  -> 待人工处理
```

## 3. 失败字段

中台至少保存以下字段：

| 字段 | 含义 |
|---|---|
| `failure_code` | 稳定的机器判断码 |
| `failure_reason` | 面向业务人员的失败原因 |
| `failure_summary` | 原因、建议和页面细节汇总 |
| `send_status` | 当前发送结果 |
| `account_id` | 实际执行账号 |
| `account_switched` | 是否发生自动切号 |
| `switched_from_account_key` | 切号前账号标识 |
| `next_retry_at` | 系统预计下次可重试时间 |
| `manual_required` | 是否需要人工处理 |
| `dead_letter` | 是否进入死信 |

常见 `failure_code`：

- `login_required`：需要重新登录
- `stranger_daily_limit`：今日私信达到上限
- `rate_limited`：私信发送频繁
- `platform_busy`：系统繁忙
- `hourly_limit_reached`：达到每小时上限
- `recipient_privacy_restriction`：对方设置了私信隐私限制
- `verification_required`：需要二次验证
- `account_risk`：账号风控或权限限制

## 4. 轮询建议

1. 提交任务后保存 `task_id` 和提交时间。
2. 先等待 2 秒，再每 3~5 秒查询一次任务详情。
3. 遇到 `pending`、`running`、`retry_wait` 都不要重复提交。
4. 轮询到终态后停止：`status=success`、`status=failed`、`status=manual_required`，或 `queue_status=dead_letter`。
5. `retry_wait` 超过 `next_retry_at` 仍未变化时，查询任务列表和 worker 健康状态，再联系私信服务排查。

伪代码：

```text
submit -> task_id
loop:
    result = GET /tasks/{task_id}.data.result
    if result.status == "success":
        保存 success、sent、send_status、failure_reason
        break
    if result.status in ["failed", "manual_required"]:
        保存 failure_code、failure_reason、failure_summary
        break
    if result.status == "retry_wait":
        等待 next_retry_at 或继续低频轮询
    else:
        等待 3~5 秒后继续查询
```

## 5. 鉴权和安全

正式环境建议使用项目约定的 HMAC 服务间签名；临时内网联调可使用 Bearer Token。账号 Cookie 属于敏感凭证：

- 不要写入数据中台普通日志、失败截图或消息内容。
- 查询接口返回的 Cookie 会脱敏。
- 当前提交接口必须同时传账号 Cookie；应使用 HTTPS 和密钥管理系统传输、保存，并同时传稳定的 `account_id` 便于追踪账号。

## 6. 私信回复检测（数据中台调度 / 私信系统检测）

职责划分：

- **数据中台**：决定何时、对哪些已发送线索调用检测；根据返回结果写 `replied` / `reply_content`。
- **私信系统**：提供单条检测能力——打开会话、比对发出文案、返回有无对方回复及内容。

### 6.1 检测接口（主）

```http
POST /api/v1/douyin/private-message/conversations/read
Content-Type: application/json
```

请求示例：

```json
{
  "account_cookie": "sessionid=xxx; sid_guard=xxx",
  "account_key": "cookie_xxx",
  "browser_name": "chrome",
  "headless": true,
  "target_profile_url": "https://www.douyin.com/user/MS4w...",
  "sec_uid": "MS4w...",
  "expected_outgoing": "您好，看到您的留言了。",
  "task_id": "comment_dm_12_345_abcd"
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `account_cookie` / `account_cookies` | 条件 | 与 `account_key` 二选一 |
| `account_key` | 条件 | 复用本机 Playwright profile |
| `target_profile_url` | 条件 | 与 `sec_uid` 至少一个 |
| `sec_uid` | 条件 | 可拼用户主页 |
| `expected_outgoing` | **是** | 我方发出文案锚点（中台 `message_content`） |
| `task_id` | 否 | 仅追踪 |
| `browser_name` | 否 | 默认 `chrome` |
| `headless` | 否 | 默认 `true` |

成功且有回复：

```json
{
  "code": 0,
  "msg": "success",
  "data": {
    "ok": true,
    "outgoing_found": true,
    "has_reply": true,
    "latest_peer_reply": "多少钱",
    "peer_replies": ["多少钱"],
    "delivery_verified": true,
    "messages": [
      {"role": "self", "text": "您好，看到您的留言了。"},
      {"role": "peer", "text": "多少钱"}
    ],
    "failure_code": "",
    "message": ""
  }
}
```

检测成功但尚无回复：`has_reply=false`，`latest_peer_reply=""`，`outgoing_found=true`。

找不到发出文案：`ok=true`，`outgoing_found=false`，`has_reply=false`，`failure_code=outgoing_not_found`（中台**不要**据此标 replied）。

检测失败示例：`ok=false`，`failure_code=login_required` / `message_button_failed` / `conversation_not_found` / `browser_error`。响应不回显 Cookie。

中台消费建议：

| 返回 | 中台动作 |
|---|---|
| `ok=true` 且 `has_reply=true` | 标 `replied`，写回复内容 |
| `ok=true` 且无回复 | 保持 `sent`，更新已读时间 |
| `ok=false` 或 `outgoing_found=false` | 记失败/不确定，不标 replied |

### 6.2 基于任务的检测（可选）

```http
GET /api/v1/douyin/private-message/tasks/{task_id}/replies
```

从已提交任务读取 Cookie、主页、发出文案，内部复用同一套检测逻辑。任务不存在返回 404。

### 6.3 说明

- 判定规则：定位与 `expected_outgoing` 匹配的我方气泡，只认**该条之后**的对方（`peer`）气泡。
- 我方事后手动再发消息（`self`）不会被当成对方回复。
- 账号级盯号（`conversation-monitors`）不是「某条线索有没有回」的依据。

## 2. 生产机私信长期失败的原因

### 2.1 AISec 代码被启动流程回退

生产 AISec 原来使用 GitHub 的 `origin/show` 分支。重启脚本会按当前分支从 `origin` 更新，因此生产一度回到了旧提交 `c45bd44`，本机已经修复的浏览器自动化代码没有持续在线。

表现：

- 私信抽屉打开后，任务很快切换到下一个任务；
- 输入框和发送按钮在不同窗口尺寸下被裁切或看不到；
- 生产代码中没有 `--start-maximized`。

处理方法：

1. 将生产现场改动完整保存为可恢复 stash。
2. 从 Gitee 拉取 `codex/integrate-machine23`。
3. 将生产分支切换到 `ad244fa`，并把 `origin` 统一为 Gitee。
4. 同时启动 Web 和 worker，确认 `0.0.0.0:7860`、HTTP 200 和 worker 存活。

### 2.2 私信编辑器回读校验过严

旧代码在填写消息后立即用严格的 DOM 文本比较判断是否成功。抖音私信编辑器会改变换行、空格、零宽字符或 DOM 文本结构，导致“实际已填入”被误判为“编辑器验证失败”。

`ad244fa` 的处理：

- 等待编辑器真正出现；
- 将编辑器滚动到可见区域；
- 填充失败时最多重试 3 次；
- 对换行、空格和零宽字符做归一化后再比较；
- 有头浏览器使用 `--start-maximized`。

### 2.3 数据中台生成请求超时

数据中台调用的是：

```text
POST /api/v1/private-message/generate
```

生产日志显示该接口常见耗时约 10～21 秒，而 comment-kit 原配置为 20 秒。接近 20 秒的请求会被 comment-kit 客户端判定超时，前端于是恢复到初始状态，看起来像“加载几秒后生成失败”。

另外，生产 comment-kit 的本地 `docker-compose.yml` 改动删除了 `PM_PROVIDER_TIMEOUT` 环境变量，所以容器实际继续使用 `config.json` 中的 20 秒配置。

`8e0edf0` 的处理：

- 私信生成请求使用独立超时，默认 60 秒；
- 发送任务接口继续使用原来的 `timeout` 配置；
- 支持 `PM_PROVIDER_GENERATE_TIMEOUT` 或 `private_message_provider.generate_timeout` 单独覆盖。

该提交已推送 Gitee，但生产 comment-kit 仍需先处理脏工作区后，才能按正式发布流程上线。

### 2.4 抖音二次验证不是代码故障

生产 worker 日志还出现过大量 `verification_required`。这表示抖音触发了二次验证或风控，任务会按设计进入 `manual_required`、`failed` 或 `dead_letter`，不是 worker 没有消费任务。

处理方法：

1. 查看任务详情中的 `failure_code`、`failure_stage`、`failure_summary` 和失败截图。
2. 出现 `verification_required` 时，先在人工浏览器完成验证。
3. 验证完成后再继续测试发送，不要用代码绕过抖音验证。

1. 先确认 Web 和 worker 都在运行：

   ```powershell
   Get-NetTCPConnection -LocalPort 7860 -State Listen
   Get-Process python -ErrorAction SilentlyContinue
   ```

2. 再查健康接口：

   ```powershell
   Invoke-WebRequest http://127.0.0.1:7860/api/health -UseBasicParsing
   ```

3. 任务失败优先看结构化字段，再看失败截图和 worker 日志。
4. 区分“提交成功/入队成功”和“worker 已消费/发送成功”。
5. 生产部署只使用约定的发布脚本，不直接在服务器改代码，不使用 `git reset --hard`，不删除数据卷。

当前 AISec 本机与生产机已经统一到 `ad244fa`，浏览器默认最大化，Web、worker 和 7860 健康检查正常。此前私信长期失败是“生产代码被 GitHub 启动流程回退 + 编辑器校验过严 + 数据中台 20 秒超时 + 抖音二次验证”共同造成的；其中前三项已有代码或部署修复，二次验证仍需人工按抖音流程处理。
